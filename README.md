# Домашнее задание №2: Сервис «ФизКат»

Консольное приложение для учёта парка самокатов, велосипедов и вещей (шлемов, док-станций).

## 1. Как собрать и запустить
* **Среда:** Visual Studio 2022 (или любой компилятор с поддержкой C++17).
* **Сборка:** Открыть `Project1.slnx`, нажать `Ctrl+Shift+B` (Собрать решение).
* **Запуск:** `Ctrl+F5` (Запуск без отладки).
* Проект использует стандарт **C++17** (для `std::make_unique`, `enum class`).

## 2. Схема наследования
Реализовано два независимых абстрактных базиса:
1. `InventoryItem` (файл `Inventory.h`) — всё, что стоит на балансе. Содержит чисто виртуальные `inventoryId()`, `name()`, `describe()`, `print()`.
2. `EnergyConsumer` (файл `Inventory.h`) — всё, что потребляет энергию. Содержит чисто виртуальный `dailyEnergy()`.

**Схема классов:**
```text
InventoryItem
├── Transport (файл Transport.h)
│   ├── Bike
│   ├── ElectricScooter
│   └── EBike
├── Helmet (файл Things.h)
└── Dock (файл Things.h)

EnergyConsumer
├── Transport (файл Transport.h)  <-- Множественное наследование
└── Dock (файл Things.h)          <-- Множественное наследование

Множественное наследование:
Класс Transport наследует одновременно InventoryItem и EnergyConsumer.
Класс Dock (вещь) также наследует одновременно InventoryItem и EnergyConsumer.
Ромбовидного наследования и virtual public удалось избежать, так как базисы InventoryItem и EnergyConsumer являются независимыми и не наследуют друг друга.
 Это упрощает архитектуру и исключает неоднозначность при приведении типов.

3. Использование smart-указателей
В проекте задействованы все три типа умных указателей:
std::unique_ptr: Парк (Fleet::items_) хранит std::vector<std::unique_ptr<InventoryItem>>.
 Парк является единоличным владельцем всех объектов. При выполнении команды remove объект автоматически уничтожается, память освобождается, а утечек не возникает.
std::shared_ptr: Используется для хранения спецификаций моделей (ModelSpec).
 Если добавить два самоката одной модели (например, ModelX), они будут ссылаться на один и тот же объект ModelSpec через shared_ptr.
 Модель жива, пока жива хотя бы одна единица техники этой модели. Для кэширования моделей используется шаблонный Registry<shared_ptr<ModelSpec>, 16>.
std::weak_ptr: Используется для реализации «витрины» (команды focus и show_focus).
 Поскольку парк владеет объектами через unique_ptr, напрямую сделать weak_ptr на них нельзя. Поэтому используется прокси-объект FocusInfo.
 Парк хранит weak_ptr<FocusInfo>. Это позволяет безопасно отследить, была ли сфокусированная позиция удалена.
 Если её удаляют, weak_ptr истекает (expired), и show_focus выводит removed вместо имени.

4. Исключения (файл Errors.h)
Создана собственная иерархия исключений, унаследованная от std::runtime_error:
Базовый класс FleetError — для всех ошибок приложения.
InspectionRejected — бросается в ServiceCenter::inspect, если в имени добавляемого транспорта есть подстрока "broken" (без учета регистра).
InvalidArgument — бросается при некорректных аргументах команд (пустой id, дубликат id, отрицательная энергия, score вне диапазона 1..10, неизвестная команда).

5. Шаблоны (файл Registry.h)
Реализован шаблонный класс template<typename T, int Cap> class Registry — реестр фиксированной емкости с методами add, size, operator[] и printTo.
Где используется: В классе Fleet как кэш моделей: Registry<std::shared_ptr<ModelSpec>, 16> models_. Это позволяет переиспользовать shared_ptr для одинаковых моделей.
Явная специализация: Реализована специализация template<int Cap> class Registry<std::string, Cap>, которая переопределяет метод печати, выводя строковые элементы в кавычках.
Специализация используется для хранения и вывода лога удаленных ID.

6. Перегрузка операторов (файл Inventory.h)
operator<< (свободная функция) — используется для печати позиции баланса в формате id name.
 Делегирует вызов виртуальному методу print() конкретного класса.
operator< (свободная функция) — используется для сравнения позиций по инвентарному номеру.
 Применяется в std::sort при выводе списка list и отчета novice.

 7. Креативная часть
Отчёт show_focus: Добавлена команда для просмотра текущего объекта на витрине, которая корректно обрабатывает состояния "активен", "удален" и "не задан"
Разделение спецификаций моделей (ModelSpec): При добавлении техники с одинаковым именем модели (например, "ModelX") они разделяют один shared_ptr на спецификацию.
Это экономит память и позволяет в будущем менять параметры модели централизованно для всего парка.
Шаблонный кэш: Реализован Registry как кэш моделей, чтобы шаблон реально использовался в бизнес-логике приложения, а не был "мертвым" кодом.
